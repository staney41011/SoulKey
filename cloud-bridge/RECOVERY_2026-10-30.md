# SoulKey production pipeline: 2026-10-30 recovery status

The central English Finals and all historical translation rows remain immutable.
Do not reset/delete the existing P259 queues or Google Sheet tabs.

## Translation
- Cloud Run `translation-queue.js` uses cross-job QA receipts only if all source IDs and the exact English Final revision match.
- Only one idempotent complete-language batch is uploaded instead of repeatedly reading the entire output Sheet per eight rows.
- Failed jobs are auto-requeued with bounded retries and backoff (6h for 429, 45m otherwise). No unlimited quota retry.
- Deployment of Cloud Run is still required; a GitHub commit alone does not change the running backend.

## Audio (legacy production engine)
- `central_tts_source.py` reads the SHA-verified English Final plus exact matching translation+QA receipts from central Sheets. No new AI translation inside audio.
- `central_tts_recovery.py` reuses `tts_runner.render_natural_language`, the old block cache, alignment/duration checks, MD5-based Drive readback, canonical names, and per-language status events.
- The GitHub Actions CPU workflow is scheduled every three hours **only if repository variable `SOULKEY_TTS_DRIVE_READY=true`**. Manual dispatch is also available.
- Protect `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REFRESH_TOKEN` in **GitHub repo Settings → Secrets and variables → Actions → Secrets**, not source files.
- Never paste these values in an issue, chat, PR, or log.
- Once set, run the workflow manually once, inspect actual `TTS_DRIVE_VERIFIED` and the Drive MP3+WAV+manifest, then enable the readiness variable.
- Missing video duration yields a listening preview marked `needs_review` rather than a fake formally complete MP3.
- Kaggle CLI-pushed kernels do not reliably carry Kaggle Notebook Secrets; use the GitHub CPU route rather than repeating the failing Kaggle kernel push.

## Current external blocker

The initial private Kaggle CPU attempt ran, but failed before fetching any source with `GOOGLE_CLIENT_ID` unavailable. The GitHub repo currently needs the protected Google OAuth credentials set up before end-to-end Drive audio can be verified.

## Verification criteria
1. `英文定稿索引` has correct task ID/revision.
2. Target text QA receipt is present, with all IDs and no duplicates.
3. Audio manifest contains exact English backup revision, source SHA, voice profile and audio receipts.
4. `04_音檔` contains a nonempty MP3 (and WAV if marked done), with Drive metadata readback.
5. `tts:<lang>` status is `done` or `needs_review`, never success based on a GitHub Actions green check alone.
